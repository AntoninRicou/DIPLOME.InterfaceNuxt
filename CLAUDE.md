# FRAMEWORK

`interface_nuxt` uses **Nuxt 4.x.x**.

All implementation, conventions, directory structure, composables, server routes, and APIs must follow the official Nuxt 4 documentation:

* https://nuxt.com/docs

Do NOT rely on Nuxt 2 or Nuxt 3 patterns when they differ from Nuxt 4. When in doubt about an API, directory layout, or lifecycle behavior, refer to the Nuxt 4 documentation rather than assuming continuity from earlier versions.

The goal right now is to prepare the Interactive interface architecture independently before connecting it to the Feedback visualization system.

At this stage:

* `interface_nuxt` is the active system being developed
* `project` should be considered as an external future receiver
* communication between the two systems will happen later through the server layer

So the architecture inside `interface_nuxt` should already be designed with the idea that:

* selected image IDs
* navigation history
* active central image

will eventually be transmitted to `project`.

For now:

The current server layer mainly exists to prepare this future connection between:

* the Interactive interface (`interface_nuxt`)
* and the Feedback visualization system (`project`)

So `project` should temporarily be treated as a passive receiver that will later subscribe to the interaction state generated by `interface_nuxt`.

# VIEW FLOW / STATE PROGRESSION

The views should not behave like traditional pages or routes.

They are progressive interface states.

The progression is:

```js id="z0ry8j"
VIEW-1 → VIEW-2 → VIEW-3
```

Once the system enters VIEW-3, it should never return to:

* VIEW-1
* VIEW-2

Those states only exist during the beginning of the experience.

However, inside VIEW-3 itself, navigation remains reversible.

The user must be able to:

* return to previously selected images
* revisit earlier navigation states
* reactivate older central images from the navigation history

So the irreversible logic only applies to the global progression of views, not to the relational navigation history once VIEW-3 is active.

---

# VIEW-1

VIEW-1 reuses the existing "disperse" state already present in the project.

This state displays hoverable and clickable images.

When the user selects an image:

* the image ID is stored in the global selectedImages array
* the system transitions permanently to VIEW-2
* the selected image should be stored but not displayed yet

The important point is that the image already exists in memory before becoming visually central later.

---

# VIEW-2

VIEW-2 is mostly textual.

It should behave like a simple timeline / transition state.

The goal is to create a temporary intermediate phase between:

* image selection
* relational exploration

The transition from VIEW-2 to VIEW-3 can later happen:

* either automatically after a duration
* or through a user action

This behavior does not need to be finalized yet.

---

# VIEW-3

VIEW-3 is the main relational interface state.

The previously stored image now appears at the center of the interface.

This central image becomes the active relational reference.

Around this image:

* the 4 relation components must react independently
* each component connects to its own JSON dataset
* each component queries the server using the central image ID
* each component retrieves nearby/related images according to its own coordinate system

The important point is that:

* all components receive the same central image ID
* but each component computes different proximities and relations

## VIEW-3 — COMPONENT LAYOUT

The 4 relation components are arranged in a fixed 2×2 grid:

```text
[ component-1 ]  [ component-2 ]
[ component-3 ]  [ component-4 ]
```

This layout is stable and does not change during VIEW-3.

Each component has:

* its own independent coordinate system
* its own relational JSON dataset
* its own proximity computation logic

However:

* all components share the same central image ID
* all components react to the same navigation state

The separation is intentional:

* layout remains stable for readability
* meaning diverges through internal spatial computation

Do NOT make the components spatially drift or re-layout themselves.
Spatial complexity belongs to the internal canvas systems, not the UI structure.

The server acts as the intermediary layer between:

* the global selected image state
* and the relational datasets used by the components

Inside VIEW-3:

* every newly selected image is added to the navigation history
* previously selected images remain accessible
* the user can reactivate older images as the central image again

The navigation history therefore behaves as a persistent relational memory.

For now the goal is only to validate:

* state progression
* image storage
* central image propagation
* server queries
* relational retrieval
* reactive component updates
* reversible navigation inside VIEW-3

# INTERFACE_NUXT VS PROJECT — CLEAR SEPARATION OF RESPONSIBILITIES

It is important to clearly separate the responsibilities of the two systems.

---

## INTERFACE_NUXT

`interface_nuxt` is the Interactive interface.

Its role is to:

* manage user interaction
* manage view progression
* store selected image IDs
* maintain navigation history
* propagate active image states
* trigger relation queries
* communicate with the server layer

This system should primarily behave as:

* an interaction state machine
* a navigation controller
* a relational orchestration layer

It should NOT become:

* the spatial rendering engine
* the visualization system
* the camera system
* the map interpolation system

---

## PROJECT

`project` is the Feedback visualization system.

It already contains:

* the spatial renderer
* the camera system
* the projection system
* point interpolation
* drift behavior
* morphing between maps
* path rendering
* persistent visual memory

This system receives interaction states from `interface_nuxt`
and transforms them into spatial visual behavior.

The long-term architecture is therefore:

```text id="bofgnf"
interface_nuxt → produces interaction states
server / socket layer → transmits those states
project → spatializes and visualizes them
```
